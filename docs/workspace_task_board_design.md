# 工作区任务看板设计

## 目标

在工作区内提供一个轻量、持久化的任务入口，允许用户手动添加普通任务、缺陷或需求，并与现有缺陷/需求自动化任务在同一看板中浏览。

参考 `dashi-taskboard` 的本地优先、状态列、任务卡和乐观版本设计，但当前实现适配 Textual TUI 与既有开发工作流，不引入独立 Web 服务或第二套执行引擎。

## 核心边界

- **手动任务**：本地看板记录，可标记为普通任务、缺陷或需求，仅用于计划、说明、优先级与进度管理。
- **ONES 待处理缺陷**：进入看板时，通过现有网页逆向接口自动查询当前用户在本工作区项目、迭代内状态为“待处理”或“重新打开”的缺陷。
- **自动化流程任务**：现有缺陷/需求工作流的只读投影；点击后进入原任务详情。
- 新建手动任务不会自动分析、修复、提交代码或创建 PR/MR，也不会被视为 ONES 中的权威缺陷或需求。
- 自动化流程仍遵循现有审批、人工验证与发布约束；看板状态不授权任何流程动作。
- ONES 卡片使用查询时生成的一次性候选快照；点击后必须明确选择“仅分析”或“分析并修复”，然后进入现有缺陷流程。
- 已存在自动化流程的同一缺陷不会再次显示为 ONES 待处理卡片。
- 数据按工作区稳定标识隔离，不允许通过编辑把任务迁移到另一工作区。

## 看板结构

| 列 | 手动任务 | ONES 实时缺陷 | 自动化流程 |
| --- | --- | --- | --- |
| 待处理 | `todo` | 待处理、重新打开 | 尚未开始的 `CREATED` |
| 进行中 | `in_progress` | — | 除 `CREATED`、`COMPLETED` 外的状态，包括阻塞和失败 |
| 已完成 | `done` | — | `COMPLETED` |

失败或阻塞的自动化流程保留在“进行中”，并使用警示色展示，避免把“结束执行”误解为“工作完成”。

## 手动任务字段与交互

- 标题：必填，最多 160 字符。
- 说明：可选，最多 4000 字符。
- 类型：普通任务、缺陷、需求。
- 优先级：低、中、高。
- 状态：待处理、进行中、已完成。
- 创建时间、更新时间与版本由系统维护。

用户可在任务看板中：

1. 点击“添加任务”创建规划任务。
2. 点击规划卡片打开编辑表单，并通过状态字段移动看板列。
3. 删除时进行二次确认。
4. 点击自动化流程卡片进入原任务详情。
5. 点击 ONES 待处理缺陷，选择“仅分析”或“分析并修复”后进入现有流程。

## 持久化与一致性

- 使用运行目录下私有 SQLite 文件 `.planning-tasks/planning_tasks.sqlite3`。
- 保存和删除均使用乐观版本检查，防止两个界面互相覆盖。
- 查询必须携带工作区标识；控制器再次验证该工作区仍存在且映射未变化。
- 存储错误只向 TUI 返回固定、非敏感提示。

## 响应式布局

- 宽终端使用三列横向看板。
- 中窄终端将三列纵向堆叠，避免卡片和按钮越界。
- 每列独立滚动，卡片保留标题、来源、摘要、更新时间与明确的进入动作。

## 后续能力

当前版本不包含拖拽、标签、负责人、截止日期、评论和附件。后续若增加，应继续保持本地规划记录与权威 ONES/工作流状态分离，并为跨进程修改保留版本检查。
