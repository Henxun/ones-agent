# Git 工作流规范

## 1. 适用范围

本规范主要约束 **ones-agent 仓库自身的开发协作**。产品替用户修改业务仓库时，必须遵循 [Agent 工作流长期约束](developer_workflow_constraints.md)；本规范的手工 Git 示例不构成产品内的提交、推送或发布授权。

## 2. 分支与工作区

- 默认采用主分支加短期任务分支，通过 PR/MR 合并；不额外引入长期 `develop` 分支。当前远端默认分支为 `main`，实际操作前确认目标仓库和目标分支。
- 分支名称使用 `<type>/<short-description>`，例如 `feat/workspace-filter`、`fix/task-recovery`、`docs/development-standards`；必要时附加工作项编号。Codex 创建的分支默认使用 `codex/<short-description>`，用户指定时遵循用户命名。
- 一个分支围绕一个可审查目标，避免混入无关重构、格式化或运行产物。
- 开始前检查状态、差异及已有 worktree；保留他人的未提交改动。需要并行或隔离时创建独立 worktree，不清空原工作区。

下例假设 `origin/main` 是已确认的目标，且当前工作区适合切换分支：

```console
git status --short
git diff
git fetch origin
git switch -c docs/development-standards origin/main
```

## 3. 提交规范

提交标题格式为 `type(scope): 中文摘要`，`scope` 可省略。摘要必须使用中文，直接说明行为变化，不得使用纯英文摘要；必要的技术名称、标识符和缩写可保留英文。`type` 和 `scope` 沿用英文约定。

| type | 用途 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `refactor` | 保持外部行为的结构调整 |
| `docs` | 文档与规范 |
| `test` | 测试新增或调整 |
| `perf` | 性能优化 |
| `build` / `ci` | 依赖、打包或自动检查配置 |
| `chore` | 其他维护 |
| `revert` | 回退已有变更 |

例如：`fix(workflow): 保留旧任务的审批恢复入口`。破坏性变更使用 `!` 标识，并在正文写明兼容影响和迁移方法；该标记本身不授权破坏兼容性。

- 提交应逻辑完整、可审查、可回退；同一行为的实现、必要测试和文档一起提交。
- 暂存明确的文件或差异块，使用 `git diff --cached` 核对；有无关改动时不要直接 `git add .`。
- 不提交 `.env`、凭据、运行数据、克隆仓库、虚拟环境、临时测试目录或日志。需要新增忽略规则时明确目录用途，不掩盖应审查的源码。
- 不伪造工作项关联、测试结果或空修复；上游已包含修复时记录验证结论。

## 4. 同步与冲突

- 同步前先 `git fetch origin` 并检查目标分支变化。仅个人、尚未共享的提交可整理或 rebase；共享分支默认 merge 更新基线，保留他人历史。
- 解决冲突时理解两侧意图，不能机械接受一侧。完成后重新检查差异，重跑受影响测试。
- 不默认执行强推、`reset --hard`、`clean -fd` 或删除未知 worktree；涉及历史重写或数据删除，先明确受影响范围并取得对应授权。
- 产品内基线更新必须走现有恢复机制：保留旧工作区，在新工作区迁移并重新测试、审查；不得用手工 rebase 或旧审批绕过快照检查。

## 5. PR/MR 与验证

提交前运行与变更相称的测试和 `git diff --check`，并核对暂存差异。测试范围遵循 [代码规范](code_standards.md)。PR 描述至少包含：

```markdown
## 问题与变更
触发条件、原有行为、修改后的行为及影响范围。

## 验证
实际执行的命令与结果；未执行、失败或跳过的项目及原因。

## 兼容与回退
配置/接口/数据影响、迁移步骤，以及回退方式；不适用时说明。

## 待验证项
需要人工或外部环境完成的验证、验收标准及所针对的提交/制品。
```

- PR 标题描述最终变更；正文面向未参与开发的审查者，不堆积调试过程。
- 本地必要检查通过且没有待修代码问题后，可用 Draft PR 交接未执行的人工/外部验证，明确缺少的历史失败证据；不要求默认在 Draft PR 前完成所有实机验证。
- 实际失败、运行未结束、冻结文件或快照不一致不能改写成“待验证”。显式严格模式仍遵循产品原有约束。
- 后续代码、测试、范围或基线变化后，更新验证证据；产品内审批绑定变化必须重新审批。

## 6. 合并、发布与回退

- 合并前由维护者确认审查问题已解决、针对当前提交的必要检查通过、所需人工/外部验证完成或相关限制已明确评估，并满足托管平台规则。
- 默认建议 squash merge 保持任务级历史；需要保留多提交关系时由维护者选择平台支持的合并方式。本文不宣称远端已配置分支保护或必需 CI。
- 合并与发布分别授权；发布前检查制品、迁移和发布验收条件。Draft 状态或 `merge_readiness=passed` 不代表发布就绪，也不触发自动合并。
- 产品创建 Draft PR 后保持 `WAITING_PR_VERIFICATION`；人工验证记录不得自行将任务标记为 `COMPLETED`。
- 已共享的错误变更优先通过 `git revert <commit>` 新增回退提交并审查验证，保留历史。涉及数据或配置迁移时评估代码回退是否足够；必要时采用兼容修复。
- 合并后仅在确认无未保存工作且无需保留恢复证据时清理任务分支/worktree；不自动清理产品保留的旧工作区。
