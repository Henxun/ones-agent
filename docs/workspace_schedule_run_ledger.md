# 工作区定时任务运行台账与租约恢复

## 目标

本阶段为工作区定时任务增加可持久化的运行批次、逐缺陷结果和崩溃恢复基础，
但不改变现有调度入口和执行流程。现有 `dispatch` 仍复用
`query_defects → analyze_defect/start_defect → confirm_repository`，且不会自动审批、
提交、推送或发布。

## 兼容边界

- 现有 `schedules` JSON 记录不增加必填字段，旧计划可原样读取。
- 现有 `claims` 表增量增加运行批次、领取时间和状态列；旧占位标记为
  `legacy_reserved`，不会被自动释放。
- 新表与旧 FastAPI `Engine` 中的 `scheduled_tasks`、`scheduled_task_runs` 无关。
  本阶段不迁移、不合并，也不改变旧 API 返回结构。
- `dispatch` 已改用原子运行台账；旧 `claim_due`、无批次参数的 `reserve_defect`、
  `record_run` 和 `finish` 继续保留兼容语义。

## 数据模型

### 运行批次

`schedule_runs` 保存：

- 计划 ID、计划版本和完整计划快照；
- 触发来源：定时、人工或 API；
- 状态：运行中、成功、部分成功、失败或中断；
- 开始时间、心跳时间、租约截止时间和结束时间；
- 发现、跳过、启动和失败数量；
- 失败阶段与安全、限长的错误信息。

计划快照属于运行证据。编辑或删除计划不会改变或删除历史批次。
同一计划最多存在一个运行中批次。

### 运行明细

`schedule_run_items` 按批次和顺序保存缺陷 ID、显示名称、执行方式、结果状态、
工作流 Run ID 以及限长原因。它不保存凭据、本机路径或完整 ONES 原始响应。

## 原子领取

定时领取在一个 SQLite `BEGIN IMMEDIATE` 事务中完成以下动作：

1. 选择一个已到期且没有运行中批次的启用计划；
2. 推进该计划的下次执行时间；
3. 保存计划快照并创建运行租约。

人工/API 立即执行同样原子创建批次，但必须校验计划版本，不改变计划的启用状态
和下次执行时间。暂停计划也可由明确的人工操作执行一次。

## 租约与崩溃恢复

创建批次时生成不可猜测的租约令牌。只有持有令牌、批次仍为运行中且调用时尚未
到达租约截止时间的执行者可以：

- 延长心跳和租约；
- 写入运行明细；
- 完成批次。

每次心跳、写明细和完成批次都在对应写事务内重新校验截止时间，不能依赖恢复扫描
先改变状态。恢复操作只处理中止时间已经到期的运行批次，将其标记为 `interrupted`。
未到期租约不会因为另一个 TUI 或进程启动而被抢占。恢复后，旧执行者的后续写入会被拒绝。

恢复不会释放缺陷占位。已有工作流 Run ID 的占位可能对应正在或已经执行的真实任务；
尚未记录 Run ID 的占位也可能处于进程崩溃边界。两者都必须由后续界面结合任务列表
明确核对，不能因租约超时盲目重跑。

## 后续接入

当前 scheduler dispatch 在启动一轮前恢复过期批次，原子创建定时运行，并在候选被跳过、
占位、创建工作流或需要人工核对时更新同一条逐缺陷明细。普通异常会闭合为失败批次；
进程退出等非普通异常保留运行中批次和永久占位，等待租约恢复，不会盲目重跑。

永久去重占位与对应的 `reserved` 明细在同一个 SQLite 事务中写入，并同时校验运行租约。
进程在占位写入与明细写入之间退出时，事务整体回滚，其他进程不会观察到无明细的孤立占位。

只读历史接口必须携带工作区标识，并通过持久化的运行快照范围过滤；运行列表和逐项明细
都使用有上限的 `limit` 与有界 `offset`。查询某个运行明细时会先验证父运行属于该工作区，
不存在与跨工作区读取返回相同的不可用错误，避免泄露其他工作区的运行标识。

后续阶段应增加独立的调度服务和“立即执行”界面。再后续由非 TUI Runtime 工厂向
FastAPI 提供相同服务，旧定时 API 在保持兼容读取的前提下逐步退役。
